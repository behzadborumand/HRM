# Local setup for rewrite

Install .NET 10 SDK/runtime and SQL Server. Keep a separate empty destination database and supply its connection string through environment or user secrets. Do not use the legacy `HRMS_BHR` database. Run each module's EF migrations explicitly after reviewing the target database name. The host must not migrate or seed automatically on startup.

Set `ConnectionStrings__HrmsNext` to the destination connection string through environment or user secrets. After reviewing and applying each module's migrations, set `HRMS_BOOTSTRAP_USER`, `HRMS_BOOTSTRAP_PASSWORD` (at least 14 characters), and `HRMS_BOOTSTRAP_COMPANY`, then run `dotnet run --project src/HRMS.Next -- --bootstrap` exactly once. The bootstrap creates a company, a default department and an administrator. It will not change an existing account. Remove the bootstrap variables afterward. Run the host with `dotnet run --project src/HRMS.Next`. No publish or IIS deployment has been performed.

For each context, use `dotnet ef database update --project src/HRMS.Next --startup-project src/HRMS.Next --context <AccessDbContext|OrganizationDbContext|PersonnelDbContext|LeaveDbContext>` only after inspecting the destination connection string and installing SDK 10. Initial migrations were generated with EF Core 9 and require verification or regeneration with EF Core 10. The application does not apply migrations automatically.

For a disposable SQL trial only, use the idempotent scripts in `database/` against `HRMS_Next_Trial_20261108`. Set `HRMS_TEST_CONNECTION` to that database to run the SQL integration test. After building the host, `powershell -NoProfile -ExecutionPolicy Bypass -File tools/SqlWebSmoke.ps1 -AppExe <path-to-host-exe>` tests HTTPS login and employee create/edit; it creates and cleans up isolated test rows. The script refuses any other database name.
